# Auditoría Estructural de Base de Datos — Plataforma REDYTELCA

## 1. Metodología aplicada

Crucé tres fuentes: (a) el DDL real en `bd_redytelca.sql`, (b) las sentencias `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE` que cada `.php` ejecuta en runtime (que en varios casos **difieren del dump**, lo cual ya es un hallazgo en sí mismo), y (c) el consumo real de esas tablas por parte de `app.js`, `index.html` y cada endpoint. Una tabla solo se considera "viva" si existe al menos una operación CRUD activa desde el flujo que realmente usa el usuario final (`index.html` + `app.js`), no desde código huérfano.

---

## 2. Hallazgo crítico #1: dos sistemas de RBAC conviviendo sin integrarse

Tu proyecto tiene **dos arquitecturas de permisos completas, redundantes y desconectadas entre sí**:

**Sistema A — el que realmente opera** (usado por `login.php`, `auth_state.php`, `permisos_listar.php`, `permisos_guardar.php`, `app.js` → sidebar dinámico):
```
usuarios → rol → modulos → paginas → rol_modulo_pagina
```
Autenticación por token persistido en la tabla `sesiones` (canal header + fallback query string).

**Sistema B — código muerto que nadie invoca desde la interfaz**:
```
usuarios(?) → roles → permissions → role_permission → user_role
             permisos → rm_permiso
             user (tabla de usuarios paralela, nunca poblada por el login real)
```
Vive en `api/roles.php`, `api/permissions.php`, `api/role_permissions.php`, `api/clientes_listar.php`, `includes/auth.php` (con `has_permission()`/`require_permission()` basado en `$_SESSION['id_rol']`) y en `roles_admin.php`, que **es una página HTML huérfana**: no está enlazada desde `index.html`, no aparece en el sidebar, no la navega ningún usuario.

Evidencia mecánica de por qué está muerto: `includes/auth.php` valida contra `$_SESSION['id_rol']`, pero tu autenticación real (`login.php`) trabaja con tokens en la tabla `sesiones` transmitidos por header `X-Session-Token` — **la sesión PHP nativa nunca se sincroniza entre requests del SPA** porque cada fetch no envía cookies de sesión de forma consistente con ese flujo. Es decir, aunque quisieras usar `api/roles.php` hoy, fallaría con 401 en la mayoría de los casos.

**Tablas huérfanas por esta duplicación:** `roles`, `permissions`, `role_permission`, `user_role`, `permisos`, `rm_permiso`, `user`.

## 4. Hallazgo crítico #3: el dump SQL no refleja el esquema real en producción

`bd_redytelca.sql` define:
```sql
`tickets`.`estado` ENUM('no leido','leido','resuelto') NOT NULL
`tickets`.`id_cliente` INT NOT NULL
`tickets`.`id_servicio` INT NOT NULL
```
Pero `api_tickets.php` ejecuta en cada request:
```php
ALTER TABLE tickets MODIFY COLUMN estado VARCHAR(30) NOT NULL DEFAULT 'Abierto'
ALTER TABLE tickets MODIFY COLUMN id_cliente INT NULL
ALTER TABLE tickets MODIFY COLUMN id_servicio INT NULL
```
y el frontend trabaja con valores `Abierto`/`En proceso`/`Cerrado` — que **nunca calzan con el ENUM original**. Esto significa que cualquier instalación fresca desde `bd_redytelca.sql` sin dejar correr primero `api_tickets.php` fallaría con `SQLSTATE[01000]: Warning: 1265 Data truncated`. Lo mismo aplica a `olts.codigo`, `servicios.id_naps`, y a la tabla `sesiones` completa, que **ni siquiera existe en el dump** pese a ser crítica para que el login funcione.

Esto es deuda técnica de "esquema fantasma": el sistema vive de auto-reparación (`ensureColumn()`, `ensureInfraSchema()`) repetida en 6 archivos distintos, en vez de tener una fuente de verdad única.

## 5. Comparativa contra arquitecturas de referencia de ISP CRM/Billing

Los sistemas de gestión de ISP a nivel administrativo (Splynx, UISP CRM, Sonar, Wisphub, Powercode) — descartando el módulo de aprovisionamiento de red que tú mismo excluyes por alcance de tesis — convergen en el mismo set de dominios funcionales:

1. **Customer Management** — ficha de cliente, estado comercial, histórico → **tienes esto**, parcial
2. **Service/Subscription Management** — plan contratado, fecha de alta, ciclo de facturación → **tienes el esqueleto (`servicios`), pero sin gestión real de planes**
3. **Billing & Payments** — factura, método de pago, estado de cuenta, mora → **tabla existe, funcionalidad cero**
4. **Ticketing/Helpdesk** → **implementado y funcional**
5. **Field Operations/Tasks** → **implementado y funcional**
6. **Network Inventory** (nodos/OLT/NAP/CPE, sin automatización) → **implementado, salvo `equipos`**
7. **RBAC + Audit Trail** → **RBAC funcional (Sistema A), auditoría inexistente**
8. **Notifications** (recordatorios de pago, vencimiento, tickets) → **inexistente**
9. **Customer Self-Service Portal** → tienes `portal_cliente.php`, pero es un mockup estático sin conexión a `pagos`/`servicios` reales
10. **Reports/Dashboard** → **implementado, con datos parcialmente simulados** (ej. `ticketsAbiertos` en dashboard se calcula con una fórmula matemática ficticia, no con `COUNT()` real sobre `tickets`)

El punto 3 (Billing) es la brecha más grave frente al estándar de la industria: un sistema que se presenta como "gestión de ISP" sin poder registrar un pago ni mostrar estado de cuenta no cubre la necesidad administrativa núcleo que tu propio `IMPROVEMENTS.md` identifica bajo "Finanzas".

## 1. Modelo de identidad de tres capas

### 1.1 Por qué NO reutilizar `usuarios`/`rol` para clientes
Un cliente no es un "rol con permisos reducidos" — es una entidad de negocio distinta (tiene `cedula`, `id_cliente`, facturación asociada) que nunca debe poder navegar `configuracion`, `roles`, ni ningún módulo del backoffice, ni por accidente de una fila mal marcada en `rol_modulo_pagina`. Mezclarlos sería un error de modelado con implicación de seguridad real: un bug de permisos podría filtrar acceso administrativo a un cliente. Separar por tabla es la barrera de aislamiento más simple y auditable.

### 1.2 Tabla nueva: `clientes_credenciales`
```
id_credencial   INT PK AUTO_INCREMENT
id_cliente      INT NOT NULL, FK -> clientes.id_cliente, UNIQUE (1 cuenta por cliente)
username        VARCHAR(50) NOT NULL UNIQUE   -- por defecto = cédula, editable
password        VARCHAR(255) NOT NULL          -- hash (password_hash(), ver nota seguridad abajo)
correo_recuperacion VARCHAR(80) NULL
estado          ENUM('activa','suspendida') DEFAULT 'activa'
creado_en       TIMESTAMP DEFAULT CURRENT_TIMESTAMP
ultimo_acceso   DATETIME NULL
```

**Nota de seguridad que corrige deuda técnica existente:** hoy tu tabla `usuarios` (staff) guarda `password` **en texto plano** (`login.php` compara `$userRow['password'] !== $password` directo). Para `clientes_credenciales`, que es la superficie de ataque más expuesta por naturaleza (miles de clientes vs. un puñado de operadores), implementaremos `password_hash()`/`password_verify()` desde el día uno. Aprovecharemos la migración para además corregir `usuarios` al mismo estándar — te lo marco como tarea de Fase 1, no de esta tabla nueva.

### 1.3 Sesión de cliente: extender `sesiones`, no duplicarla
En vez de crear una tabla `sesiones_cliente` paralela (que reintroduciría el mismo antipatrón de duplicación que acabamos de eliminar en Fase 1), extiendo la tabla `sesiones` existente con un discriminador:

```
sesiones
  id_sesion       INT PK AUTO_INCREMENT
  token           VARCHAR(64) UNIQUE
  tipo_usuario    ENUM('staff','cliente') NOT NULL DEFAULT 'staff'   -- NUEVO
  id_referencia   INT NOT NULL   -- id_usuario si staff, id_credencial si cliente
  creado_en       TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  expira_en       DATETIME NOT NULL
```

`auth_state.php` y `login.php` se bifurcan internamente según `tipo_usuario`, pero **el mecanismo de token (header `X-Session-Token` + fallback query string) se reutiliza tal cual** — ya está probado, funciona, y no hay razón de ingeniería para reinventarlo para el portal.

### 1.4 Endpoints nuevos del portal de cliente
- `login_cliente.php` → valida contra `clientes_credenciales`, emite token con `tipo_usuario='cliente'`
- `cliente_estado_cuenta.php` → `GET`, requiere token de cliente, devuelve `facturas` + `pagos` **solo del `id_cliente` dueño del token** (nunca acepta un `id_cliente` del query string — se resuelve server-side desde el token, para que un cliente no pueda pedir el estado de cuenta de otro cambiando un parámetro)
- `cliente_pago_registrar.php` → `POST`, inserta en `pagos` con `estado='pendiente'` — nunca valida el pago (esa autoridad sigue siendo exclusiva del staff en el módulo Finanzas del backoffice)

### 1.5 `portal_cliente.php` deja de ser mockup
Se reescribe como vista real: login → fetch de estado de cuenta → formulario de pago conectado a `cliente_pago_registrar.php`. `router.php` mantiene el mapeo `/cliente` → este archivo, sin cambios de enrutamiento.

## 3. DDL de las entidades financieras y de contrato (definición cerrada)

```sql
-- FACTURAS: la obligación
CREATE TABLE facturas (
  id_factura        INT AUTO_INCREMENT PRIMARY KEY,
  id_servicio       INT NOT NULL,
  periodo           VARCHAR(7) NOT NULL,           -- '2026-07'
  monto             DECIMAL(10,2) NOT NULL,
  fecha_emision     DATE NOT NULL,
  fecha_vencimiento DATE NOT NULL,
  estado            ENUM('pendiente','pagada','parcial','vencida','anulada') DEFAULT 'pendiente',
  creado_en         TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_factura_servicio FOREIGN KEY (id_servicio) REFERENCES servicios(id_servicio)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- PAGOS: el evento (reestructura de la tabla actual del dump)
CREATE TABLE pagos (
  id_pago             INT AUTO_INCREMENT PRIMARY KEY,
  id_factura          INT NULL,                    -- nullable: pago a cuenta sin factura previa
  id_cliente          INT NOT NULL,
  id_servicio         INT NOT NULL,
  monto               DECIMAL(10,2) NOT NULL,
  fecha_pago          DATETIME NOT NULL,
  metodo_pago         ENUM('transferencia','pago_movil','zelle','efectivo') NULL,
  referencia_bancaria VARCHAR(255) NULL,
  estado              ENUM('pendiente','validado','rechazado') DEFAULT 'pendiente',
  fecha_validacion    DATETIME NULL,
  id_usuario_valido   INT NULL,                     -- staff que validó (FK usuarios)
  origen              ENUM('portal_cliente','backoffice') DEFAULT 'backoffice',  -- trazabilidad de quién originó el registro
  CONSTRAINT fk_pago_factura   FOREIGN KEY (id_factura) REFERENCES facturas(id_factura),
  CONSTRAINT fk_pago_cliente   FOREIGN KEY (id_cliente) REFERENCES clientes(id_cliente),
  CONSTRAINT fk_pago_servicio  FOREIGN KEY (id_servicio) REFERENCES servicios(id_servicio),
  CONSTRAINT fk_pago_usuario   FOREIGN KEY (id_usuario_valido) REFERENCES usuarios(id_usuario)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- CONTRATOS
CREATE TABLE contratos (
  id_contrato    INT AUTO_INCREMENT PRIMARY KEY,
  id_servicio    INT NOT NULL,
  fecha_inicio   DATE NOT NULL,
  fecha_fin      DATE NULL,                         -- NULL = indefinido
  tipo_contrato  ENUM('indefinido','plazo_fijo','promocional') DEFAULT 'indefinido',
  estado         ENUM('vigente','vencido','rescindido') DEFAULT 'vigente',
  observaciones  TEXT NULL,
  creado_en      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_contrato_servicio FOREIGN KEY (id_servicio) REFERENCES servicios(id_servicio)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Añadí `origen` a `pagos` respecto a lo que habíamos hablado — es un campo de trazabilidad barato que responde de inmediato "¿este pago lo registró el cliente desde el portal o un operador manualmente?", dato que un jurado de tesis valorará como evidencia de integración real entre los dos sistemas.
